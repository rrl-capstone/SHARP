# How this repository is organized, and why

The aim: anyone on the team can clone the repository, set two personal settings, run one
command, and get the same results; and anyone reading it can answer "where does this run, and
what does it use?" by opening one file.

## What we took from how others do it

**dbt** ("How we structure our dbt projects",
https://docs.getdbt.com/best-practices/how-we-structure/1-guide-overview) is the standard tool
for organizing SQL pipelines. Its main ideas are what this layout follows:

- **Layers in order.** Raw data in, then cleaned building blocks, then the tables people use.
  Here: `1_cohort` to `6_care_quality`, each stage building on the ones before it.
- **One table per step, named for what it is.** `pwh_cohort`, `person_year_conditions`,
  `quality_measures`; no `tmp` or `final2`.
- **Sources declared once.** dbt names each raw table in one place. Here every schema name
  and study year comes from `config/`, rendered into the SQL as `${komodo_schema}`,
  `${work_schema}` and so on.
- **Tests next to the models.** dbt runs `unique` and `not_null` tests on each table. Here
  each step ends with its own checks, and `-- expect: rows_total = person_years` stops the run
  when a table has duplicate person-years.

We use these ideas without dbt itself, because two of the six stages are not SQL (Lifei's
matching is R, Rhea's Gagne score is Python, and dbt runs only SQL on Redshift), and because the
big Komodo scans must run one year at a time to stay within Redshift Spectrum's time limit,
which dbt does not do simply. If the project grows, moving the SQL stages into dbt is
straightforward: each step is already one table with its checks.

**OHDSI's SqlRender** (https://ohdsi.github.io/SqlRender/) is how OHDSI studies keep SQL
portable: SQL files carry parameters such as `@cdm_database_schema` instead of real schema
names. Our `${work_schema}` placeholders are the same idea. This is what lets Lifei's SQL,
which was written for her own schema, run in anyone's.

**Cookiecutter Data Science** (https://cookiecutter-data-science.drivendata.org/) is a common
layout for analysis projects. We follow its rules on data: raw data is never edited or
committed, code lists and settings are files under version control, and results are
regenerated by the code rather than edited by hand.

## The layout

| Path | What it holds | Rule |
|---|---|---|
| `config/study.yml` | Every study setting: years, sample or full, matching ratio, caliper, Gagne levels | The only place a setting changes |
| `config/local.yml` | Your Redshift username and driver folder | Never committed (`.gitignore`) |
| `pipeline/<stage>/` | The steps, in run order within each stage | One table (or a few related ones) per step, with its checks |
| `runner/` | Reads the settings, renders and runs each step, saves results | `runner/steps.py` is the single list of what runs, in order |
| `reference/` | Code lists: conditions, procedures, drugs, measures, Gagne lookups | Change codes here, not in the SQL |
| `results/<run>/` | Aggregate results of a run, and `run_info.json` | Counts 1 to 10 hidden; regenerated, never edited |
| `tests/` | Checks that run without the database (`python -m pytest`) | Run before every commit |
| `notes/` | Proposal, plan, methods decisions, literature, this note | |

## What makes a run reproducible

1. **Settings in one file.** `results/<run>/run_info.json` records the commit, whether there
   were uncommitted changes, and the full `config/study.yml` used.
2. **Pinned packages.** `requirements.lock` pins every Python package version the code was
   tested with.
3. **Repeatable choices.** The 1% sample (MD5 of the patient ID) and the 20 controls per case
   (MD5 of ID and year) pick the same people every run; matching sorts rows first, so MatchIt
   pairs the same people.
4. **Rerunnable steps.** Every step drops and rebuilds its own tables, so rerunning one step,
   or resuming with `--from`, gives the same tables as a full run.
5. **History.** Commit `e06303d` is the teammates' code exactly as supplied. Every change since
   is in the git history, so any earlier result can be rebuilt from its commit.
